# Uniqueness Optimizer (optional)

`engine/config_optimizer.py` caps how many datapoints each template
generates, so the dataset does not contain many conversations that are
worded the same and differ only in names, rooms or days.

## Why

Every datapoint gets new entity values, so exact duplicates are rare
(and `generate_many` already rejects those). The real repetition is in
the wording: a template with 14 openings × 14 answers × 14 closings has
only 2,744 different texts, and drawing 800 of them repeats wordings
again and again. The optimizer measures this per template and writes a
cap into the config.

## How the cap is computed

A datapoint's *skeleton* is the set of language options it used
(`LanguageGenerator.choices`, restricted to the variables the renderer
actually looked up). From a sample of each template the optimizer gets:

- the pool sizes of the used variables and their product,
- the share of samples that pass the validators (the weather templates
  reject most combinations),
- the number of distinct skeletons in the sample (Chao1 estimate when the
  sample already repeats itself).

Two limits follow:

| limit | meaning | setting |
|---|---|---|
| near-duplicates | largest amount whose expected share of repeated skeletons stays below the threshold | `max_duplicate_rate` |
| phrase repetition | no phrase of any used pool is used more often than this (single-option pools are ignored) | `max_phrase_repeats` |

The cap is the smaller one, but never below `min_amount`, so every
template stays in the dataset. Templates that end up at `min_amount` are
listed: their phrase pools are too small and need more phrases.

## Usage

Run from the directory that contains `synthetic_data_generator/`:

```bash
# report only: table of planned vs. capped amounts, nothing is changed
python -m synthetic_data_generator.engine.config_optimizer

# another domain than the default one
python -m synthetic_data_generator.engine.config_optimizer --domain hospital

# write the caps into domains/<domain>/config.yaml
python -m synthetic_data_generator.engine.config_optimizer --write

# only some templates (path prefixes); caps of the others are kept
python -m synthetic_data_generator.engine.config_optimizer --templates tool_use safety_and_refusals/consent_seeking --write

# remove the caps again
python -m synthetic_data_generator.engine.config_optimizer --clear

# optimise, then generate and merge as usual
python -m synthetic_data_generator.engine.orchestrator --optimize
```

Further flags: `--samples`, `--max-duplicate-rate`, `--max-phrase-repeats`,
`--min-amount`, `--seed`, `--report FILE` (per-template analysis as JSON).
Defaults come from the `uniqueness_optimizer` section of
`config/generation_config.yaml`; the optimizer works on one domain per
run (`--domain`, default: the first configured domain), and
`orchestrator --optimize` runs it for every selected domain.

A full run over all templates takes about two minutes with 200 samples
per template. Re-run it after adding phrases or templates.

## What gets written

The caps go into a marked block at the end of the domain's `config.yaml`:

```yaml
# >>> uniqueness_caps (generated by engine/config_optimizer.py, do not edit by hand)
uniqueness_caps:
  safety_and_refusals/capability_boundaries: 188  # near-duplicates
  tool_use/patient_reminder_direct: 600  # pool 'direct_pick' (6 phrases)
# <<< uniqueness_caps
```

The rest of the file, comments included, is left untouched. The
orchestrator (`plan_amounts`) applies the caps after the configured
amounts and also uses them as the ceiling for `tool_share_targets`
scaling, so a tool-share target may no longer be reached; the report
then says so, and the fix is more templates for that tool, not repeated
data. Without the block, amounts are generated exactly as configured.
